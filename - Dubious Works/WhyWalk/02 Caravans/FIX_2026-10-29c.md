## 1. Nothing animated at all — `BONE_GROUP.Arms`

```
[18:18:00.353 E] Can't start L@0x1[scripts/whywalk/ridinganim.lua];
  Lua error: [string "scripts/whywalk/ridinganim.lua"]:102: Key not found: Arms
```

The diff between your upload and what I shipped is one line:

```lua
[anim.BONE_GROUP.Arms] = anim.PRIORITY.Weapon,
```

There is no `Arms` bone group. The members are `LowerBody`, `Torso`,
`LeftArm`, `RightArm` — and `BONE_GROUP` is an engine enum that **raises** on
a name it does not have rather than returning nil. That is a load failure, so
`ridingAnim.lua` never started and **nothing in the suite animated** — no
rider pose, no boat pose, no caravan passenger. One key cost every animation
in the mod.

Corrected to `LeftArm` and `RightArm`, which keeps what your edit was reaching
for. **Be aware it is inert as written, deliberately.** A priority is only
consulted for a bone group the blend mask includes, and the mask is
`LowerBody + Torso`. To make those two entries bite you would need

```lua
local RIDE_BLEND_MASK = anim.BLEND_MASK.LowerBody + anim.BLEND_MASK.Torso
                      + anim.BLEND_MASK.LeftArm + anim.BLEND_MASK.RightArm
```

— but that hands the arms to the riding clip, and free hands for weapons and
spells while mounted is the requirement this controller was built around. Say
the word if you want the arms in and I will do it properly; I did not assume.

## 2. The strider had no animation — the record list was swept, not indexed

The log says the vehicle fell back to an activator, and an activator cannot
animate. But your load order certainly has silt strider creatures in it:
vanilla's, plus a Wild Silt Striders mod.

The lookup swept `pairs(types.Creature.records)` looking for a model path. It
found nothing and **raised nothing**, which is the signature of iterating
something that is not a table. `RecordList` is annotated
`table<integer|string, T|nil>` in Cod3x. The documentation also says `records`
"may be **indexed by recordId**", and there is a documented
`types.Creature.record(id)` returning a record or nil.

So the lookup now **indexes first** — `siltstrider`, `a_siltstrider`,
`siltstrider_vanilla` — and only then sweeps, as a capability probe that costs
the sweep and not the journey. The matched record's model is still checked, so
a load order that reuses the id cannot get a cat cloned into a caravan. And
the match is now on the **basename**, so a replacer that moves
`Siltstrider.nif` into its own folder still matches.

It also says what it did, every session:

```
[WhyWalk Caravans] strider creature cloned from siltstrider
  (found by record id siltstrider); legs will animate.
```

and if it still cannot, it now names every id it tried instead of just
shrugging.

## 3. Vivec → Seyda Neen: the route data is corrupt

Not a code bug. The imported route has a **stray point**:

```
vivec -> seyda neen : 37 points
  segment 29 jumps 73,468 units, then segment 30 comes 71,924 straight back
  turn at that point: 178 degrees
  next longest segment in the whole route: 5,097
```

Of its 204,146-unit "length", **145,392 is that one out-and-back spike**. It is
not the longest route in the data, it is a broken one. At 1400 u/s that is 51
seconds out and 51 back, which is exactly what you saw: direction change
halfway, then what looks like being stuck.

The existing validation only checks where a route **starts and ends**, and both
of this route's ends are fine. So it now also rejects a **segment grossly out
of scale with the rest of its own route**, which is what a stray point looks
like. Measured across all 47 shipped routes, longest segment ÷ median segment:

| route | ratio |
|---|---|
| `vivec -> seyda neen` | **50.5** ← corrupt |
| `suran -> balmora` | **27.0** ← corrupt (already caught by its endpoint) |
| `seyda neen -> vivec` | 6.7 ← worst well-formed route |
| `bosmora -> sailen` | 4.7 |
| … | |
| `molag ruhn region -> tel gilan` | 1.5 |

The threshold is 10: 1.5× above the worst good route, 2.7× below the better of
the two bad ones. A **ratio**, not an absolute length, because segment scale
varies legitimately between routes (median 1329 to 2364). Tortuosity separates
these two as well (4.84 against 1.50) but would also condemn a genuinely
winding mountain road; the outlier test names what is actually wrong.

The route is dropped and `findRoute`'s reverse fallback uses
`seyda neen -> vivec` walked backwards — 30 points, 62,166 units, no stray
point. Your next log will say:

```
[WhyWalk Caravans] route dropped, reverse used instead: vivec -> seyda neen
  (stray point: segment 29 of 36 jumps 73468, 51x the median for this route)
```

Both directions stay available, because both corrupt routes have an intact
opposite. That is asserted, not assumed.

## 4. A mid-journey save threw away the whole block

```
[18:28:52.844 E] Global[.../caravans_global.lua] onSave failed:
                 Value is not serializable.
```

`guideHomeCell` is a **Cell**, which is not a serialisable value — and the
engine rejects the **entire table** when one appears in it. So that save
stored nothing from this module at all, `vehicleRecordId` included, which
means the next journey minted another record and the guide was never returned
to their post. One bad field cost the whole block.

Stored as the cell's **name** now. A name round-trips: `teleport` takes a cell
name, and an empty string means the default exterior worldspace — which is
what an exterior cell's `name` already is, so one field serves both kinds
without a flag.

## The pattern, and a new checker

Three of these four are the same mistake: **an engine value annotated as a
table in Cod3x, used as if it were one.**

| | what happened |
|---|---|
| `I.UI.MODE` | `type(M) ~= 'table'` was always true, so travel never intercepted |
| `types.Creature.records` | `pairs()` found nothing, so the vehicle could not animate |
| `anim.BONE_GROUP.Arms` | raised at load, so nothing animated anywhere |

Every existing checker passed on the `Arms` file — luacheck, check_names,
check_declorder, globalcheck, check_handlers, check_load, ctxcheck, api_sweep,
check_anims, all clean on code that could not load. `check_load` comes closest
and is the most misleading: its stubs answer any key, which is exactly the
behaviour the engine does not have.

**`tools/check_enums.py`** reads the member list of every engine enum out of
the Cod3x annotations and checks each `module.ENUM.Member` in the source
against it. Validated three ways, as this project's checkers are:

- against the known bug → `line 121 NO SUCH MEMBER anim.BONE_GROUP.Arms
  has: LeftArm, LowerBody, RightArm, Torso`
- against all 19 suite files → clean
- against 117 third-party Lua files (UI Toolkit, Immersive Travel, Ben's,
  DropinUtils, Devilish Guar Riding, p37z, Trusty Truck) → **zero** false
  positives

I also checked it is not inert: it resolves and confirms **291 valid** enum
member uses across those two codebases. A checker that passes everything is
indistinguishable from one that does nothing, and mine was exactly that at
first — its own string-stripping turned every `require('openmw.animation')`
into `require('')`, so no alias resolved and nothing was checked. It reported
0 findings on the bug it was written for. Caught because it was run against
that bug before being trusted.

`check_enums.py` is now in all three modules' `tools/`, wired into
`check_all.sh`, and Caravans has a `check_all.sh` for the first time. The
toolchain is also now identical across the three modules — `check_declorder`,
`check_names` and `luacheck` were missing from some of them.

**The harness now models the engine, not the annotation.** `Creature.records`
answers a direct index and yields **nothing** from a sweep — precisely what
your log shows, no error and no match. A variant that raises instead is
covered separately, since another build may do that. And the save test asserts
on **types**, because that is what the engine actually rejects: strings,
numbers, booleans, a GameObject and a `util.Vector3` are allowed; anything
else is the next Cell waiting to happen.

The threshold test is the one I would point at. It does not assert "10 is
right" — it asserts the threshold **sits in a gap**, with the two bad routes
above it by 2× and the worst good route below it by 30%. A threshold that only
works on today's data is tuned by luck, and that test would catch it stopping
being true.
