# Caravans — the mesh faces backwards (2026-11-03b)

Your diagnosis was right, and the answer was in my own codebase the whole
time.

> the issue with collision seemed to be stemmed from the strider beginning the
> journey facing the opposite direction and having to swing wildly around to
> correct

**The strider mesh faces -Y, and Caravans never accounted for it.** From
`boats_db.lua`, written weeks ago:

> `yawOffset`: object yaw = bow heading + yawOffset. **Vanilla-orientation
> meshes have the bow at -Y** (Stormrider: object angle = travel − 180),
> Immersive Travel's `_rot` copies have it at +Y

Every vanilla-orientation hull in Boats carries `yawOffset = PI` —
`ex_de_rowboat`, `ex_gondola_01`, `ex_longboat`, `sc_newboat00`. Immersive
Travel ships `_rot` copies of its meshes precisely because the originals face
the other way; `a_riverstrider_rot.nif` is one of them.

`r\Siltstrider.nif` is a vanilla-orientation mesh. Caravans had **no offset at
all**.

So every round of heading work — the lag filter, the lookahead, the 2π unwrap,
the steering model, the stateless bearing — computed a correct direction of
travel and then handed it to a mesh that does not point that way. The strider
faced backwards, swung wildly at the start of a journey trying to correct, and
drove into the scenery doing it. Each fix made the *input* better and the
output was mirrored regardless.

Boats solved this weeks ago and I never asked the question of Caravans.

```lua
yawOffset  = math.pi,
```

Applied in `placeVehicle` and nowhere else, because the player and the guide
are ordinary actors whose meshes face the standard way. With no filter left in
the facing, frame one is now correct — which is the snap you asked for.

## The black screen: a cell frozen at boarding

`s.cell` is captured when you board and never changes, and it was handed to
every teleport for the whole journey — three objects, sixty times a second,
named into a cell they had long since left.

Cod3x on that argument: *"If the worldspace has multiple cells (i.e. an
exterior), the destination cell is calculated using `position`"*, and an empty
string *"means the default exterior worldspace"*. So naming a cell is wrong
for an exterior journey — the position already determines it — and naming a
**stale** one asks for a worldspace move every frame. "The screen blacks out
constantly" and "cell transitions are more jarring" is what that looks like.

Core already did this correctly (`player.cell or ''`) and Boats passes the
object's **live** cell. Caravans was the only one freezing it. An interior is
still named, because an interior is its own worldspace and a position cannot
imply it.

## The root-motion lurch, now that the IT assets load

> the strider walks ahead and jumps back as if it is using a broken root
> motion loop

That is exactly what it is. `runforward` carries root translation, and for a
non-actor OpenMW applies that translation to the object's node — while we are
*also* moving the object along the route. The mesh walks forward under its own
animation and snaps back each loop.

This is not fixable from Lua: `playBlended` has no root-motion switch, and the
alternative — moving the object less to compensate — would stop it following
the route. The options are the walk cycle with the lurch, or `idle` without
it, and the activator was already falling back to `idle` before you added the
assets. I have left the fallback chain alone rather than choose for you; if
you would rather it always played `idle`, that is a one-line change to
`FALLBACK` in `caravans_vehicle.lua`.

## The 0.52 test environment: `00 Core/testenv/suites/test_wwapi`

I could not run it — the engine build is not in the tarball and the download
is blocked from here (403). So I wrote the suite instead, and you have the
engine:

```sh
cp -r "00 Core/testenv/suites/test_wwapi" <testenv>/suites/
cd <testenv> && ./run_tests.sh suites/test_wwapi --verbose
```

It tests the **engine**, not WhyWalk. Every probe in it replaces an inference
that cost a round trip:

| probe | what it cost |
|---|---|
| `types.Creature.records` — table? iterable? | swept with `pairs`, found nothing, raised nothing; two rounds of a strider that could not animate |
| `anim.BONE_GROUP` members, unknown key | `.Arms` **raised**, so `ridingAnim` never loaded and nothing animated |
| `I.UI.MODE` / `I.UI.WINDOW` type and keys | `type(M) ~= 'table'` always true; travel interception stood down on every menu |
| `createRecordDraft` model path | passed bare, throws; boarding failed nine times in one session |
| two teleports in one frame | the teardown did it, threw, left a second strider at the stop |
| the yaw convention, roll vs yaw | probed in three modules with a self-consistent test that checks nothing |
| `playBlended` on a missing group | a silent no-op — correct, and why three rounds went unanswered |

It prints what it finds as well as asserting, and the printout is the point.

**What it cannot answer**, and this is worth knowing before you run it: no
`.kf` and no real meshes, so animation *groups*, text keys and mesh bounds are
out of reach — which includes the two questions that have cost the most, which
groups a mesh carries and which way it faces. Those need real data, and the
in-game diagnostics now cover them.

Both fixes are pinned, verified by reverting them:

- **the mesh offset** — the harness now asserts the vehicle carries one, and
  that its rendered yaw is the travel heading *plus* that offset, while the
  guide's yaw is the travel heading with no offset. Two assertions that
  distinguish the mesh frame from the travel frame, which nothing did before.

  assertions require it to be the worldspace rather than a frozen cell. With
  the stale cell restored they fail.

The second one is the shape I should have been writing all along: the mock had
been ignoring that argument entirely, so the bug was invisible to 94 passing
assertions.
