# Caravans — journeys that never ended, and the camera (2026-10-29b)

## 1. The journey never finished — one line, one traceback

Your log names it exactly:

```
[02:27:39.080 E] Global[.../caravans_global.lua] onUpdate failed.
                 Lua error: Object is either removed or already in the
                 process of teleporting
[02:27:39.080 E] 	[C]: in function 'teleport'
[02:27:39.080 E] 	caravans_global.lua:290: in function 'endJourney'
[02:27:39.080 E] 	caravans_global.lua:567: in function <...:498>
```

**An object can be teleported once per frame.** A second call before the first
has landed raises, and it is a hard error that kills the whole handler.

The teardown ran inline at the end of `onUpdate`, in the same frame that had
just placed the vehicle, the player and the guide. Its first statement parks
the vehicle — a second teleport of an object already teleported that frame —
so it threw every single time, at line 290.

`session = nil` runs before that, which is why the error appears **once per
journey** rather than once per frame, and why it is easy to miss. Everything
after the throw never ran:

| never ran | what you saw |
|---|---|
| park the vehicle | a second strider standing at the stop |
| release the guide | the caravaner carried off their post |
| put the player down | stuck aboard |
| send `ARRIVED` | no dismount message, and the seated pose stayed on |

Your whole first report, from one line.

### The fix: the teardown gets a frame to itself

`endJourney` is now a **request** — it records the reason and returns.
`finishJourney` does the work from the top of the next `onUpdate`, before
anything has moved. One frame of latency, and no call site can get the
ordering wrong.

Not just "skip the placement on the last frame", because that does not cover
the abort path: pressing X arrives as an **event**, which the engine may
deliver in a frame where `onUpdate` has already placed everything. Both
orderings are now tested.

### I had this log in front of me last time and missed it

The same error is in the 10-28 log, four times, with the same traceback. I
grepped for the `[WhyWalk Caravans]` print prefix and for the module name, and
never looked for errors raised *by* the script. The answer to a bug you had
not yet reported was already on screen.

## 2. The camera: not us, but caused by us

Caravans never touches the camera — I checked, there is no `camera` call in
the module — and Core explicitly refuses to pin first person (*"that is not
acceptable here, since the whole point of a rider animation is being able to
look at it"*).

What is in your log is **VvardenfellDirector**, 4116 times:

```
[VvardenfellDirector] teleport; normal camera restored
```

Once per frame, and the long runs line up exactly with the journeys:

| run | from | to | frames |
|---|---|---|---|
| journey 1 | 02:26:32.454 | 02:27:39.087 | 2199 — ends **at the teardown error** |
| journey 2 | 02:28:43.403 | 02:29:48.946 | 1225 — ends at the next one |
| ordinary door teleports | elsewhere | | 20–30 each |

It is not alone. `DetailDevil`'s own `onTeleported` handler raised three
times, and **all three are inside journey windows**:

```
L@0x1[scripts/detaildevil/ash/player.lua] onTeleported failed.
Lua error: DelayedAction is not allowed to create another DelayedAction
```

**The cause is ours.** A teleport fires `onTeleported` on *every* player script
in the load order. Carrying the player by teleporting them each frame delivers
sixty of those a second to every other mod in your list. Nothing was written
expecting that.

### The fix: use the pin Core already built for this

Core's MWScript bridge moves the player with `SetPos` instead of a teleport,
and the comment at `placeRiderMWScript` records why it exists — *"Devilish
warns that a per-frame Lua player teleport loop triggers an engine bug
involving nearby NPCs, which is why this is the preferred path when it
actually works."* The same hazard, found from the other end.

So the pin is now published as the `WhyWalkRiderPin` interface rather than
duplicated. Caravans asks Core to carry the player; everything that makes the
pin safe comes with it — the stale-ESP probe, the liveness check that catches
an `.omwaddon` shipping the script as source text with no bytecode, and the
automatic fall-through to a teleport when the bridge is dead. An owner token
stops a mount and a journey pinning the same player at once.

Core loads at `#852` and Caravans at `#858`, and the interface is read at call
time, so ordering is not a factor.

### Read this part before you test

**I have not confirmed that `SetPos` avoids `onTeleported`.** It is reasoning
from the mechanism, and the last time this module shipped on reasoning alone
(`I.UI.WINDOW.Travel`) the reasoning was wrong.

So the module now **says which path it used**, once per session:

```
[WhyWalk Caravans] rider carried by TELEPORT. Every frame of a journey fires
  onTeleported on every player script in the load order, which some mods react
  to; if your camera locks during a ride, that is why. The WhyWalk MWScript pin
  avoids it, and needs WhyWalk.omwaddon with the WhyWalkRiderPin script
  compiled (open and save it in OpenMW-CS).
```

The report waits ~1 second before claiming the bridge is live, because Core
allows 20 frames of misses before declaring it dead — reporting on frame 1
would print the optimistic answer and then quietly fall back.

**The likely outcome is that you still see that line**, because Core's own
warning says the shipped `WhyWalk.omwaddon` carries `WhyWalkRiderPin` as
source text with no compiled bytecode. If so, nothing about the camera changes
until you open that script in OpenMW-CS and save it. Grep the next log for
`carried by` and it will tell you in one trip.

If it says TELEPORT and you want third person now, turning off
VvardenfellDirector is the immediate workaround — and if that mod is yours
(it sits in `OpenMW mods_DBS` alongside your animation packs), the durable fix
is to make its camera restore fire on a **cell change** rather than on every
`onTeleported`, or to debounce it.

### The mock now models the rule that was missing

The old harness let an object be teleported twice in a frame. That is why a
suite of 62 assertions passed on code that could not finish a journey. It now
raises the engine's own message, and the frame counter advances per `onUpdate`.

## What to look for

1. **Arriving should actually arrive** — you on the ground, one strider only,
   the caravaner back on their post, and the arrival message.
2. **Pressing X mid-journey should do the same.**
3. **Grep the log for `carried by`.** If it says TELEPORT, the camera lock
   stays until `WhyWalkRiderPin` is compiled in your `WhyWalk.omwaddon`.
4. If it says nothing at all, the pin is live — and then check whether
   `VvardenfellDirector` has gone quiet during a ride. That is the measurement
   that settles whether `SetPos` really does avoid the handler.
