Your log answered it in one line, at `03:30:03.550`:

```
L@0x1[scripts/whywalk/caravans/caravans_player.lua]:
  [WhyWalk Caravans] this OpenMW build exposes no Travel window name through
  I.UI.WINDOW, so the travel menu cannot be intercepted. Caravans is inactive;
```

**`I.UI.WINDOW` has no `Travel` entry in OpenMW 0.51.** That was the inference
the implementation note flagged as unverified, and it was the one that was

## What `registerWindow` actually does

Cod3x says *"Register new implementation for the window with given name;
overrides previous implementation… it is only possible to override built-in
windows."* True, and I read it correctly — but it can only override windows the
engine **publishes by name**, and the travel window is not among them. The
documented sentence is about replacing a window the engine already names;
it is not a general interception hook.

## What replaced it

The UI **mode**, watched as an event. Everything it rests on comes from working
code rather than from a reading of the docs:

- **`UiModeChanged` carries `{ oldMode, newMode }`.** AnimRefresh v5 reads
  exactly those two fields in production.
- **`I.UI.MODE.Travel` exists.** Ben's Rideable Silt Striders keys its entire
  mod off `I.UI.getMode() == I.UI.MODE.Travel`, and that mod works.
- **`I.UI.removeMode(mode)`** drops a mode from the stack.

So: notice the mode change, decide whether this module can take over, close the
engine's travel window, show ours. Still event-driven — Ben polls every frame
to reach the same moment.

### Two orderings that matter

**Decide before closing.** `prepareMenu` is now split from `presentMenu`,
because once the travel window is closed there is no handing the player back to
it. The window is removed only after a menu is known to be buildable; if UI
Toolkit is missing, or there is no guide, or no imported route runs from here,
the vanilla window stays up and travel works normally.

**Close before showing.** UIToolkit's `Popups` adds its own UI mode *only when
the stack is empty*. Showing the popup first would leave it sitting under
Travel mode, and then pulling Travel out from under it gives a visible,
unclickable menu — that library's documented trap. Both orderings are asserted.

### A third thing the first version would have got wrong

Interception removes only the Travel mode, so the **dialogue** window the
travel topic was reached through is still open underneath. The journey would
have begun with the player looking at the caravaner's dialogue while the
strider walked off. `I.UI.setMode()` on departure clears it.

## The module now reports what the build exposes

Rather than inferring a third time: on the first travel menu, if `MODE.Travel`
is missing, it prints the actual key sets.

```
[WhyWalk Caravans] I.UI.MODE has no Travel entry, so the travel menu cannot be
  intercepted. ... The name lists below say what this build does expose;
  please include them in a report.
[WhyWalk Caravans]   I.UI.MODE   = Interface, ...
[WhyWalk Caravans]   I.UI.WINDOW = Inventory, Map, ...
```

Once per session, not per menu. If this fires, the next log settles the
question instead of starting another round.

Note the timing change: the old message appeared at startup, this one appears
the first time you open a travel menu — which is when it is actually true.

## `tools/test_intercept.lua` — 29 assertions, and it would have caught this

The interception shipped with no test covering it at all, which is why a broken
mechanism got as far as your game. The new suite drives the real player script
against a small engine model and asserts:

- `UiModeChanged` is registered as an **event**, not an engine handler. Under
  `engineHandlers` OpenMW rejects it outright — how AnimRefresh v4 shipped a
  feature that never ran once.
- The window is closed **before** the popup is shown.
- The menu closes **before** the journey is requested.
- `removeMode` is called **exactly once**, not recursively — it causes another
  `UiModeChanged`, and handling that would re-ask the question with the window
  already gone.
- The vanilla menu is **left alone** with no UI Toolkit, with no travel-selling
  guide, and before the route data has arrived.
- Only destinations with a route are offered; an unrouted one is dropped rather
  than offered and then failed.
- Every row has a unique `id` — duplicates make UIToolkit share one component
  between rows.
- `setItems` is called after `itemList`; an unpopulated list renders an empty
  scroll area silently.
- The diagnostic above fires once and names both tables.

Its mock `I.UI.WINDOW` is deliberately built **without** a `Travel` entry — the
state your 0.51 build is actually in. If anything starts depending on that
again, these tests stop passing.

Run against the previous implementation it fails on the first assertion
(`UiModeChanged is an EVENT handler -> nil`) and then cannot continue, because
that version had no such handler to call.

### One more self-inflicted bug, caught by the toolchain

`check_names.py` reported `possibly undefined: expose`, which traced to a `--`
**inside a string literal** in the new diagnostic message. The comment stripper
removes line comments before string literals, so the `--` ate the closing quote
and leaked a word as an identifier. This project has hit that exact hazard
before — the earlier fix was the same, replace it with `;`. Swept the rest of
the module; no other occurrences.
