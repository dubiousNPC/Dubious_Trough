# WhyWalk — the controls port

The movement model moved from "teleport the mount to a computed position" to
"write the mount's `controls` and let the engine move it". That one change is
the fix for three of the four outstanding symptoms, and it deletes more code
than it adds.

| | |
|---|---|
| **no guar animations** | fixed, and the cause was not what the architecture suggested |
| **no collision** | fixed by the port; the engine does it |
| **interior riding** | now works; gated behind a setting, default off |
| **no jittering, smooth movement** | preserved — see the note on one-frame lag |

Net: `whywalk_global.lua` is down to 295 lines of real code (from 410) with the
movement simulation gone, `whywalk_mount.lua` rewritten to 106, and the
hand-rolled gravity, ground clamp, speed easing and jump arc deleted outright.

---

## 1. The T-pose had two causes, and the second one was a constant

The architectural cause was already known: a teleport is not movement, so the
character controller was never asked to move the creature, never selected a
locomotion group, and the actor rendered at bind pose.

The second cause is why the mount script added on 2026-10-04 **did not fix it
either**, and it is worth recording on its own. That script played the gait
with:

```lua
animation.playBlended(self, group, { loops = -1, forceLoop = true, ... })
```

Cod3x's contract for `playBlended`:

> `loops` - a number **>= 0**, the number of times the animation should loop
> after the first play (default: 0)

`-1` is outside that range. `-1` means "infinite" in a great many APIs and
means "invalid" in this one. So even with a mount script attached and playing,
the group was not looping — it ran once, or not at all, and the creature
dropped straight back to bind pose. Devilish Guar Riding passes
`loops = 999999` for exactly this intent, which is why its guar animates.

Nothing in the toolchain catches an out-of-range constant. That is the third
bug in two passes whose common shape is *code that reads correctly and cannot
work* — after the declaration-order bug and the `UiModeChanged` registration.

The port makes it moot rather than fixing it: there is no scripted gait any
more. The engine picks the group and scales its playback from the movement it
is asked to perform, which is what "natural vanilla movement and animation"
actually is.

## 2. What the engine now supplies

Everything in this list was either hand-written, attempted badly, or absent:

| | before | now |
|---|---|---|
| gait selection | scripted, with a broken `loops` | engine |
| animation playback speed | none (DGR scales it by a tuned curve) | engine |
| root motion, footfalls | none | engine |
| collision, world and actors | **none at all** | engine |
| gravity, falling, landing | hand-integrated Euler arc | engine |
| ground height | heightmap, exteriors only | engine |
| step up / step down | none | engine |
| slopes, stairs, water | none | engine |
| interiors | fell through the world | engine |

The mount script's entire movement body is now:

```lua
c.movement  = throttle
c.run       = gallop and throttle > 0
c.yawChange = steer ~= 0 and (steer * turnRate * dt) or 0
c.jump      = jumpPending      -- one frame only
```

Speed comes from the creature's own Speed stat, scaled by the throttle
magnitude. That is why `PROFILE`'s `speed`, `walkMul`, `revMul` and `jump`
fields are gone rather than kept: a slow guar is now slow because it is a slow
guar, and shipping four numbers that nothing reads would have them drift away
from the behaviour they appear to describe.

## 3. Why not DGR's approach, given DGR feels better

DGR does **not** drive the controls. It teleports the creature, plays the
animation itself, and does its own collision with nine raycasts per frame
(`OBSTACLE_RAY_HEIGHTS` × `OBSTACLE_SIDE_OFFSETS`, plus ground, ceiling and
landing probes). It is a complete hand-written character controller sitting
next to the engine's own, and it works.

But what it is doing is *approximating* vanilla movement — picking a group from
a gait band and scaling playback with a fitted curve:

```lua
elseif gait == 'gallop' then
    return 0.92 + math.min(1, gaitSpeed) * 0.36
```

Driving the controls gets the real thing instead of an approximation, for five
field writes instead of nine rays. The one piece of DGR worth copying outright
is `self:enableAI(false)`, which is in — see §6.

## 4. The rider pin is unchanged, and still the only per-frame work

There is still no API to parent one object's transform to another, so the
player still has to be placed on the mount every frame, and only a global
script can teleport the player. `whywalk_global.lua`'s `onUpdate` still exists
and its first statement is still `if not session then return end`.

What changed is that it now **reads** the mount's position and heading instead
of computing them:

```lua
local mountPos = s.mount.position
local mountYaw = s.mount.rotation:getYaw()
```

That is not just shorter. It is the only correct source now that the engine is
free to stop the creature against a wall, slow it on a slope or shove it
aside — a computed position describes where the creature was *told* to go.

`session.yaw` is gone for the same reason, including from the save: the
creature carries its own rotation through a save, and a stored copy could only
ever disagree with it.

### One-frame rider lag

The mount is moved by the engine in its own handler and the rider is placed
from the result, so the rider can be one frame behind. Handler order within a
frame is not specified, so this is not removable.

It should not be visible, because the offset is *constant* rather than varying
— which is the difference between lag and jitter. DGR has the same split and
feels solid. Flagged rather than claimed fixed: if anything looks loose at
gallop, this is the place to look.

## 5. Rider state now follows the creature, not the command

`riderState` moved from the global script into `whywalk_mount.lua`, for a
context reason and then stayed for a better one.

The context reason: deriving it needs `types.Actor.isOnGround`, which Cod3x
documents as *"Can be called only from a local script"* with an `LObject`
parameter. A global script cannot call it. (`getCurrentSpeed` takes a plain
`Object` and would have been fine.)

The better reason: the pose should follow what the creature actually does.
Under the teleport model those were the same thing by construction. Now the
engine can refuse — **a mount pressed into a wall has a throttle of 1 and a
speed of 0** — and the rider should be sitting still, not pedalling. The gallop
threshold is read from the creature's own walk speed rather than hard-coded, so
a slow mount and a fast one each reach "gallop" at their own pace.

Still sent on change only, same event, same consumer (`ridingAnim.lua`).

## 6. The one assumption I could not test

The port rests on `self:enableAI(false)` disabling the AI **decision** layer
only, leaving the character controller free to act on scripted controls. Cod3x
says "Enables or disables standard AI", which supports it, and without it the
creature's own AI keeps issuing movement and fights every control write.

What the two reference mods prove, **separately and not together**:

- p37z writes `controls` on a creature and never disables AI — so controls
  demonstrably work with AI **enabled**.
- DGR calls `enableAI(false)` but teleports rather than driving — so it proves
  nothing about controls.

Neither proves controls work with AI *disabled*. So it is a switch, not a
buried call:

```lua
TUNING.suppressMountAI = true     -- whywalk_shared.lua
```

**If a mount stands still while being steered, set this to false.** Steering
will work and the creature's AI will also be free to wander, which looks like
the mount drifting or turning on its own — a combination that identifies the
cause immediately, where a silent failure would not.

The mount script's `onLoad` re-enables AI **unconditionally**, unlike the other
two sites, so a save written with suppression on and loaded with it off cannot
leave a creature's AI disabled forever.

## 7. Saddle placement from `getBoundingBox`

`mountType` is `nil` for any creature `PROFILE` has never heard of — which is
every mount another mod adds. The old fallback was the default profile:
`up = 130`, a guar's height, which puts a rider inside a boar and under a silt
strider.

### What is safe to read, and what is not

`Object:getBoundingBox()` returns a `util.Box` with `center`, `halfSize`,
`transform` and `vertices`. Cod3x documents `vertices` as "taking rotation into
account", which implies the rotation lives in `transform` and `halfSize` is in
**body** axes. That is the natural reading, but it is an inference, so the
function is built to be correct either way:

- **Vertical comes from `halfSize.z`**, which is yaw-invariant under *both*
  readings — creatures rotate about Z only, so no amount of turning changes the
  box's vertical extent. This is the number that decides whether the rider sits
  on the creature or inside it, and it can be trusted.
- **Forward is left at zero**, not derived from `halfSize.y`. Under the other
  reading that is a yaw-dependent mix of length and width, and at 45° the two
  are not separable. Zero is not a cop-out: the eight measured profiles use
  forward offsets of −6 to −12 units on bodies 100+ units long, so the box
  centre is within a few units of every hand-tuned value in the table.

The one judgement call is the vertical fraction — a quadruped's box top is its
head, not its back — so the saddle sits at `centre + halfSize.z * 0.72`. That
reproduces the guar's measured 130 to within 5 units, but it **is** a fit to
one animal, so the derived value is printed once per record:

```
[WhyWalk] 'xyz_mod_lizard' has no mount profile; saddle derived from its
bounding box as up = 134.8 (box half-height 90.0, centre 70.0 above origin).
To pin it down, add it to whywalk_shared.M.PROFILE with
saddle = { forward = 0, right = 0, up = 135 }.
```

Read it out of the log and promote it. Once per record, not per mount.

### Does the bounding box help collision?

**No, and it is worth being clear about why.** Collision is now the engine's,
using the creature's real collision shape — which is better than a box, because
it is the actual shape. Deriving anything from the bounding box to feed a
collision check would be strictly worse than what the engine already does for
free.

Where it *could* earn its place is **rider clearance**: the box gives the
rider's head height, and a ray from there would tell you whether a doorway or
ceiling will clip them. That is a real use, and it is the honest alternative to
§8's blunt instrument — but it needs `nearby`, so it belongs in
`whywalk_mount.lua`, and it is a separate piece of work.

### A leak caught on the way

Wiring this up exposed a latent aliasing bug. `profileFor` returned the shared
module-level `DEFAULT_PROFILE` **by reference** on its fallback path, and the
new code assigns `session.profile.saddle`. With the old form, riding one
unrecognised creature would have rewritten the default saddle for the rest of
the session: mount a silt strider once and every later unknown mount seats its
rider a thousand units in the air. `profileFor` now always returns a fresh
table, saddle included — one table per key press.

## 8. Interior riding, and the setting

Riding indoors is no longer broken — the engine moves the mount through
interiors exactly as it does outdoors, with full collision. The reason it is
off by default is **scale, not stability**: Morrowind's interiors are built for
a walking player, so a mount clears most doorframes only just and the rider's
head does not clear low ceilings at all.

- Registered as `ALLOW_INTERIORS` in a new **Riding** group on the existing
  WhyWalk settings page, `permanentStorage`, default off.
- Mounting in an interior is refused with a message naming the setting —
  activating a guar and having nothing happen reads as a broken mod.
- Riding *into* an interior dismounts at the door, checked on cell change,
  because the mount can now walk through load doors.

The value is read at mount time and **sent with the request**. A global script
cannot read player storage, and the value only matters at the two moments that
already carry or hold it, so there is no subscription and no per-frame read.

### A load-order fix that came with it

`I.Settings.registerGroup` takes `page = <key>`, so the page must exist first.
The page was registered in `ridingAnim.lua`, which the manifest loads **after**
`whywalk_player.lua` — so a group registered from the player script would have
preceded its own page. The page registration moved to `whywalk_player.lua`,
which loads first, making "page before group" a property of the manifest rather
than a coincidence. The camera group stays in `ridingAnim.lua`, which owns the
camera.

Every new API call was checked against the Cod3x stubs individually rather than
trusting the sweep: `Actor.isOnGround` (local-only, hence §5),
`Actor.getCurrentSpeed`, `Actor.getWalkSpeed`, `self.enableAI`,
`Object:getBoundingBox`, `util.Box`, `TeleportOptions.onGround`,
`ui.showMessage`, `core.l10n`, `storage.playerSection`, and every
`ActorControls` field.

`test_jumparc.lua` is **deleted**. It guarded the interior floor in the
hand-rolled jump arc, and that arc no longer exists — the engine jumps. A test
that passes by guarding code nobody runs is worse than no test.

`test_mountcontrols.lua` covers the three things that cannot be seen by
reading the file: that `MountStop` clears the controls *before* handing AI back
(otherwise the last written movement survives into the first AI frame and the
creature walks off), that `yawChange` scales with `dt` (it is a per-frame delta,
so without it the turn rate doubles when the framerate does), and that
`controls.jump` is a one-frame edge (held true, it retriggers forever). Plus the
case the port exists for: full throttle against a wall reads as **idle**.

### What to check in game, in this order

1. **Does the mount move at all?** If not, `TUNING.suppressMountAI = false`
   (§6). This is the one unverified assumption and everything else depends on
   it.
2. **Does the guar animate?** It should walk, run and idle with its own
   vanilla gait, speed-scaled by the engine. This is the headline.
3. **Collision.** Ride at a wall, a rock, a building. It should stop. Ride onto
   a bridge; it should stay on top of it.
4. **Interiors.** Mounting indoors should refuse with a message. Turn the
   setting on, then ride indoors and jump — it should land.
5. **Smoothness at gallop**, for the one-frame lag in §4.
6. An unknown creature from another mod, for the derived saddle line in the log.
