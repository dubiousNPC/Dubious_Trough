# WhyWalk — 2026-09-29 bug pass

Four reported symptoms. Three were single defects in this mod; one was not this
mod at all. Everything below was verified against the Cod3x 0.4 stubs, the
Devilish Guar Riding source, and the shipped `.omwaddon` binary.

---

## TWO THINGS YOU MUST DO BY HAND

These cannot be done from here and the mod is not correct until both are done.

### 1. Disable Devilish Guar Riding (or disable WhyWalk)

**This is the whole of symptom 4, and part of 1 and 2.** They are not
compatible, and the collision is not obvious from the symptoms.

`Devilish Guar Riding/.../player.lua:339`:

```lua
local function forceFirstPerson()
    local ok, mode = pcall(camera.getMode)
    if not ok or mode ~= CAMERA_MODE.FirstPerson then
        pcall(camera.setMode, CAMERA_MODE.FirstPerson, true)
    end
end
```

Called from `updateRiding` every `FIRST_PERSON_CHECK_INTERVAL` (0.10s) **for as
long as its own ride is active**. Press the POV key and DGR snaps you back
inside 100ms. WhyWalk never touches camera mode — it cannot win that fight and
does not try.

The two mods also claim the *same creature*: WhyWalk's
`MOUNT_TYPE_BY_RECORD` lists `detd_guarride1`, which is DGR's `GUAR_ID`
verbatim. Activating that guar starts **both** rides, so both pin the rider, at
different offsets, on different frames.

WhyWalk now prints a warning the first time it sees a rival mount event
(`DETD_GuarRiding_Mounted`, `DETD_HorseRiding_Mounted`,
`SimpleHorseBaseRideAttach`). Detected behaviourally, not by content-file name,
because these mods ship their Lua separately from their plugin.

### 2. Recompile the pin script in the ESP

**The shipped `WhyWalk.omwaddon` has never worked.** Parsing the binary:

```
record SCPT
  SCHD: name=WhyWalkRiderPin  numShorts=0 numLongs=0 numFloats=0
        scriptDataSize=0            <-- compiled bytecode length
  SCDT: 0 bytes                     <-- the compiled script. Empty.
  SCTX: 333 bytes                   <-- the SOURCE TEXT. Correct, but inert.
```

The globals (`whywalk_active/x/y/z/angle`) are all declared correctly, and the
script *text* is right — `player->` prefixes present, `PCGet3rdPerson` gate
present. But `scriptDataSize = 0` and `numFloats = 0` where it should declare
its four locals: the script was written into the plugin and never compiled.
**OpenMW executes the compiled SCDT, not SCTX.** The pin has been a no-op.

Fix: open `WhyWalkRiderPin` in the OpenMW-CS script editor and save it, which
compiles it. Then verify `scriptDataSize` is non-zero.

Until then WhyWalk now detects this at runtime and falls back (see below), so
it works — just on the slower path.

## Symptom 1 — rider backwards, controls reversed

**One sign error, and it caused both.** `whywalk_global.lua` placed the mount
with `rotateZ(-s.yaw)` while placing the rider with `rotateZ(s.yaw)`, one
function apart.

This was flagged in RESEARCH §3.7 as "not settled — verify in game". It is
settled now, three ways:

| source | forward convention | mount rotation |
|---|---|---|
| `stepMovement` | `fwd = (sin yaw, cos yaw)` | — |
| Cod3x `util.lua:471` | `rotateZ(a)` = rotate about `(0,0,-1)` | — |
| **Devilish Guar Riding** `guar.lua:293` | `rotateZ(yaw):apply((0,1,0))` | `rotation = rotateZ(yaw)` **positive** |

`rotateZ(+yaw) * (0,1,0)` equals `(sin yaw, cos yaw)` exactly — verified
numerically at 0/45/90/135/180/270/359°. The negation produced the exact
east–west mirror at every angle:

```
yaw  90  travel( 1.000, 0.000)  rotateZ(+yaw)( 1.000, 0.000)  rotateZ(-yaw)(-1.000, 0.000)
```

So the mount **travelled east while facing west**. Pressing D increased yaw, so
it slid right while visibly turning left — "controls reversed" — and the
correctly-oriented rider ended up facing the mount's tail — "rider backwards".

No NIF is facing −Y. The negation was simply wrong.

**Second, independent cause of the same symptom:** `placeRiderTeleport` applied
body yaw *only in third person*. In first person it passed no rotation at all,
so the body kept whatever facing it had at mount time and never realigned. The
"don't fight mouse-look" reasoning behind that is correct for the MWScript path
— where the gate is `PCGet3rdPerson`, inside the script — but on the Lua path it
meant no yaw was ever applied. `teleport`'s rotation is the **body's**, not the
camera's; first person drives the view from the camera's own yaw. Body yaw is
now set in both perspectives.

## Symptom 2 — position too low

`saddleFP` removed. It was mine, added last pass on the theory that first
person needs the body lowered because the camera sits at the head, extrapolated
from Sturdy Steed's `sdlUp1 47 / sdlUp3 80` ratio. It dropped the rider from
`up = 130` to `up = 78` — 52 units — and since DGR was locking you into first
person you were getting the lowered pose permanently.

It was never justified by the reference. **DGR uses one offset for both views**,
`PLAYER_OFFSET { right = 0, forward = -10, z = 130 }`, which is exactly
WhyWalk's third-person `saddle`. Now restored to a single pose.

First-person framing is the camera's job, and `ridingAnim.lua` already exposes
`FP_OFFSET_V` / `FP_OFFSET_H` for it (default 0). Moving the body instead
desynchronised what third person shows from where the rider actually is.

## Symptom 3 — AnimRefresh out of date

Shipped v3; **v4** has been current since 2026-09-23 and already ships in CAKE,
IED v0.65, Take a Seat v0.33 and the Bardcraft branch at the same shared path.

Relevant to this mod specifically:

- v3 watches **raw mode**, so Third↔Preview↔Vanity hops each fire a callback —
  and WhyWalk's callback re-issues a *looping pose*, restarting it from frame 0.
  Measured: 5 spurious callbacks per idle→vanity→back cycle. v4 watches the
  first-person **boundary**, which is the only thing that rebuilds the model.
- v3 delivers **4 callbacks per POV press**. v4 delivers 1.
- v3 never refreshes after Rest/Travel or after a game load. v4 does.
- WhyWalk's subscriber is a looping pose, so it should **opt out** of v4's
  `verify` pass (the opt-in second delivery) — that is the Take a Seat case, not
  the CAKE/IED VFX case.

**I did not write a v4 here on purpose.** Two mods shipping different files at
`scripts/AnimRefresh/AnimRefresh_v4.lua` occupy one VFS path and only one
survives — inventing a fifth variant is precisely the failure the version guard
exists to prevent.

`scripts/AnimRefresh/` now contains `AnimRefresh_v3.lua.REPLACE_WITH_V4` and the
manifest already points at `AnimRefresh_v4.lua`. **Copy the real v4 from Take a
Seat v0.33 (or CAKE/IED) into that folder and delete the marker file.** Until
you do, the manifest names a file that does not exist.

## Symptom 4 — camera will not change to third person

Not WhyWalk. See "Disable Devilish Guar Riding" above.

Confirmed by exclusion as well as by finding the cause: WhyWalk contains no
`camera.setMode` call anywhere, never calls `I.Camera.disableModeControl`, and
`I.Controls.overrideMovementControls` is documented in Cod3x 0.4 as affecting
only "movement controls including jump and sneak" — not POV.

## Also changed

**Bridge liveness detection.** `bridgeReady()` proved the globals *exist*; it
could not prove anything *consumes* them. With the uncompiled ESP that meant:
probe passes → `placeRiderMWScript` writes four numbers nothing reads → returns
`true` → `placeRider` returns before reaching the teleport fallback → **the
rider is silently never pinned**.

This is the same mistake as the §2.7 entry in RESEARCH ("the probe that probes
the wrong thing"), committed again in the function whose own comment warns
about it. Capability was tested; effect was not.

Now the effect is tested. `placeRiderMWScript` records the target it wrote, and
next frame checks whether the player actually reached it. 20 consecutive misses
(~0.3s) and the bridge is declared dead, once, loudly, with the recompile
instruction — and every later frame goes to the teleport pin instead.

**`--` removed from three string literals.** Legal Lua, but the suite's static
checkers strip comments naively, so `"… not found) -- falling back …"` produced
phantom `UNDECLARED running` / `UNDECLARED them` reports. Not worth the noise
when the tools are the thing keeping the mod honest.
